# REQ-20261013-114 — Stage 3 解析提示词强化 60-90 秒时长硬约束

> 父 REQ：[REQ-20261012-099](REQ-20261012-099-stage3-content-parse-rework.md) 修订十
> 状态：✅ 验收通过（2026-10-13）

## Context

**用户反馈**（2026-10-13 第五轮）：

> "上面这个是解析短视频内容阶段的提示词，你把这个提示词再完善一下。尤其是关于"字幕累计时长是否满足 60~90 秒"的要求，一定要控制它能够达到这个要求。优化之后的提示词，把它设置为系统提示词"

**现状分析**：

旧 `STAGE3_SYSTEM_PROMPT` 里的时长约束只写一句：
```
3. 时长适配：每条全部字幕合计约 60-90 秒。
```
"约"字过于宽松，LLM 实际产出经常 < 60 秒（凑不齐）或 > 90 秒（超长），用户验收时发现多条短视频时长不达标。提示词没有给出：
- 怎么估算"字幕朗读时长"（按行按字数？按真实视频？）
- 凑时长的具体手段（补哪些行 / 砍哪些行）
- 自检环节没把时长检查放在第一位 → LLM 容易忽略

## 解决什么问题

| 维度 | 旧版 | 新版 |
|---|---|---|
| 时长约束表述 | "每条全部字幕合计约 60-90 秒" | "**时长硬约束（60-90 秒）** ... 落在 60.0–90.0 秒区间（含端点），这是输出底线" |
| 时长计算口径 | 无 | 显式公式 `本行朗读秒数 = (本行字符数 + 1) / 4` + 12 行 / 22 字 = 69 秒示例 |
| 凑时长手段 | 无 | 短了：尾部追加收束 → 仍不够再延展开头；不要塞口水话 |
| 压时长手段 | 无 | 长了：先砍重复冗余 → 压成「钩子 + 论据 + 收束」三段式；不砍结论 |
| 不达标处理 | 无 | "时长不达标 = 不可输出，必须重选" 单独一段写死 |
| 自检顺序 | 时长混在"切片筛选标准"里 | **时长硬约束自检** 单独拎出来，置自检环节**第一位** |

## 关键设计决策

1. **「硬约束」+「60.0–90.0」精确数字**：去掉"约"字，括号里给精确区间（含端点），让 LLM 没空子钻。
2. **统一估算口径**：旧版没有"怎么算时长"，LLM 会按真实视频切片算（容易算短）。新版用字符数公式 `(字符数+1)/4` —— 4 字/秒 是中文播报正常语速，+1 留停顿。
3. **凑/压手段具体到行级别**：不是抽象"加内容" / "删内容"，而是"在尾部追加收束行" / "压成三段式" → LLM 拿到可执行的步骤。
4. **时长自检置顶**：把"时长硬约束自检"放在自检环节最前，不达标就回字幕重选，不进入其它标准检查。这样就算其它全过，时长不过也是不过。
5. **保留旧版所有关键词**："选题类型 / 选行规则 / 切片筛选 / 内容质量门槛 / 输出前自检 / 宁缺毋滥" 全部保留，原有 `test_stage3_system_prompt_constant` 测试零修改通过。
6. **不破坏输出格式约束**：「只输出」仍未出现（输出 JSON 格式由 `run_stage3` 在 user payload 尾部约束），避免 LLM 提前切换模式。

## 风险与对策

| 风险 | 对策 |
|---|---|
| LLM 仍可能输出不达标（公式估算是粗略的） | 公式已写成 `(字符数+1)/4`，并给 12 行 / 22 字 = 69 秒示例，LLM 可机械照算；用户验收阶段若仍不达标，可在解析后端加一道「时长后置校验」自动提示重选 |
| 凑时长手段引入口水话 | 提示词明确禁止"为了凑时长而塞入口水话或无关行" |
| 压时长手段砍掉结论 | 提示词明确"不要砍掉结论或关键论据" + 「钩子 + 关键论据 + 收束」三段式 |
| 自检环节 LLM 跳过第一步 | 时长自检置顶 + 单独成段 + "否 → 回到字幕里增/删行再算一遍，达标才进入下一项" 强约束 |
| 公式 `(字符数+1)/4` 对中英混排不准 | 中文字符算 1、英文/数字算 1 都成立；纯英文短句会被略估短，但用户主要场景是中文课，足够用 |
| 公式边界 60.0 / 90.0 严格 | 提示词写"含端点" → 边界值也算达标，LLM 不会纠结 ±0.5 秒 |
