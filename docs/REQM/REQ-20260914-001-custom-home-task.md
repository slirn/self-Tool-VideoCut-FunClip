## 1. 背景与目标

**当前状态**：FunClip fork 启动后直接进入上游 Gradio 界面（[funclip/launch.py](../../../../funclip/launch.py)）。

**目标**：在 slirn-standalone 仓库中新增一个**自定义首页**，可与原上游首页**切换使用**。新首页面向"长视频剪辑任务"的**任务管理**：列出已有任务、新建任务、配置任务参数。

**价值**：把当前"裸用 Gradio 界面"的单次剪辑流程，升级为"任务驱动"的工作流。

---

## 2. 用户故事

### US-1：切换首页

- **角色**：项目使用者
- **场景**：项目启动后，想用 slirn 的任务管理而不是上游 Gradio
- **操作**：在启动时（CLI 参数）或启动后（界面入口）选择使用哪个首页
- **结果**：进入对应的首页

### US-2：查看已有任务

- **角色**：项目使用者
- **场景**：已经做过几次长视频剪辑，想看历史
- **操作**：打开自定义首页，浏览任务列表
- **结果**：看到每个任务的摘要信息

### US-3：新建剪辑任务（核心流程）

- **角色**：项目使用者
- **场景**：有一段长视频想做剪辑
- **操作**：
  1. 点击"新建任务"按钮
  2. 选择/拖拽原始视频文件
  3. （可选）设置开始/结束时间，从视频中截取一段
  4. （可选）从公共热词库挑选热词，加入本任务
  5. 提交，任务入库
- **结果**：任务出现在任务列表，可继续后续剪辑流程

### US-4：维护公共热词库

- **角色**：项目使用者
- **场景**：项目有反复出现的领域词汇（如讲师姓名、专业术语），希望长期复用
- **操作**：在公共热词库里增/删/改热词
- **结果**：下次新建任务时可以从库中选

## 6. 非目标（明确不做）

- ❌ **不做**：分布式任务调度（单机本地）
- ❌ **不做**：多人协作（单用户）
- ❌ **不做**：任务进度实时监控（提交后状态变更）
- ❌ **不做**：视频转码/压缩（只截取）
- ❌ **不做**：引入任何数据库（MySQL / SQLite / MongoDB / Redis / ORM / KV）—— **所有数据 = 本地文件**（JSON / 纯文本 / 视频文件 / 符号链接）。详见 [REQ-001-A §0](REQ-20260914-001-A-task-data-model.md) 存储原则。

## 10. 子 REQ 拆分（**按用户选择：Epic + 子 REQ 模式**）

为避免一次性设计过大、把横向架构与子功能耦合，本 Epic 拆分为 4 个独立子 REQ，每个独立走完整 5 阶段流程。

### 10.4 Epic 与子 REQ 的边界

- **Epic（本文）**：定概貌、价值、横向约束、用户故事、关键验收标准
- **子 REQ**：每个独立写需求（细化验收标准）、独立设计、独立实现、独立验证
- **横向架构决策**（如任务数据模型、目录结构）在 **REQ-001-A 的设计阶段**定下来，B/C/D 沿用

### 10.5 用户当前的工作方式

**用户选择：C — Epic + 子 REQ**

**含义**：
- Epic 描述（本文）作为整个大主题的参考
- 用户已一次性把 **Epic 级**需求 + 答案给完（见 §5、§11）
- 我把 Epic 拆成 4 个子 REQ，每个子 REQ 走完整 5 阶段（REQM → DESIGN → 实现 → 评审 → 验证）
- 子 REQ 串行推进（A → B/C/D），每完成一个跟用户对齐再走下一个
- 遇到"必须人决策"才停下（命名、品牌、不可逆操作）

**好处**：
- Epic 横向架构（任务数据模型、目录布局）在 A 阶段定下来，B/C/D 沿用，避免各做一份
- 子 REQ 规模小（每个 5-10 条需求），实现/验证成本可控
- 用户随时可以补"我突然想到还要加 X"——这会变成 REQ-001-E 或独立 Epic

**与 `funclip-workflow-preferences` 的对齐**：
- 用户偏好是"一次性提需求 → 一直执行到底"
- Epic 模式下：用户在 Epic 这一层**已经**一次性提完；子 REQ 是我**自己**的拆分产物，不是用户再次提需求的入口
- 因此子 REQ 文档主要由我整理（细化验收标准、转化为可验证条目），用户**只 review** + 在关键节点确认
