# 阶段 2：系统设计

**目标**：把"需求"变成"实现方案"，关键决策有理由，影响范围明确。

## 入口条件

- `requirements/REQ-<id>.md` 已确认

## 产出

`design/DESIGN-<id>.md`（如涉及架构变更，附架构图）

## Checklist

### 架构层

- [ ] 列出**所有受影响文件**（含新增/修改/删除）
- [ ] 区分"上游 funclip/ 改动"和"slirn 改动"和"配置改动"
- [ ] 标注是否需要新增依赖（需用户批准）

### 关键决策

每个决策必须满足：
- [ ] 至少有 2 个备选方案
- [ ] 选定方案有**明确理由**（不是"我觉得"）
- [ ] 说明**被拒绝方案**为什么不选
- [ ] 关键决策写成 ADR 格式（Architecture Decision Record）

### 接口设计

- [ ] 函数签名（参数、返回值、异常）
- [ ] 模块间调用关系
- [ ] 数据结构（schema、字段含义）

### 边界与错误处理

- [ ] 列出会失败的场景
- [ ] 每种失败场景的处理方式（重试 / 报错 / 降级）
- [ ] 错误信息要可读（人话，不只是 stacktrace）

### 兼容性

- [ ] 是否向后兼容（旧数据/旧调用方式）
- [ ] 是否需要 migration
- [ ] 性能影响评估

### 示例

- [ ] 至少 1 个**端到端使用示例**（输入 → 中间 → 输出）
- [ ] 示例要可运行（不是伪代码）

### 完整性自检

- [ ] 工程师照着这份设计**不需要再问你**就能开工
- [ ] 设计改动局限在必要范围（不夹带私货）

## 出口条件

- [ ] 关键决策都有理由
- [ ] 至少 1 个端到端示例
- [ ] 用户（或代理）确认设计可执行

## 反例

- ❌ 只说"用 X 设计模式"而不说为什么
- ❌ 把整个架构重写但需求只是加一个小功能
- ❌ 设计里没考虑错误处理
