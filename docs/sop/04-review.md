# 阶段 4：评审

**目标**：在合并前发现缺陷，确保代码质量。

> 公共规范 `delivery.md`（根因优先原则）与本 SOP 等价（`legacy-gap`，本节「根因优先」小节是公共规范的最小子集）；`quality-gates.md` 与本 SOP 互为 `extend` 关系（按 risk 分级决定 effort 级别）。

## 入口条件

- 实现已提交（git log 可见）
- 自测通过

## 产出

- `code-review` 报告（用 `/code-review` skill）
- 评审后的 commit（fixup）

## Checklist

### 评审维度

用 `/code-review <effort>` 跑评审，effort 级别（与 `.agent/standards/quality-gates.md` 对齐）：

| 级别 | 适用 | 产出 |
|---|---|---|
| `low` | 改 < 50 行、改动局限；低风险（文案 / 格式 / 明确局部 Bug） | 少量高置信度发现 |
| `medium` | 改 50-200 行、跨模块；一般任务 | 标准发现 |
| `high` | 改 > 200 行、新功能；高风险变更 | 全面发现，可能含不确定项 |
| `max` | 架构变更、核心模块；难回滚变更 | 全部维度 |

### 必查项

- [ ] **正确性**：实现是否真满足验收标准
- [ ] **简化**：有没有可以更简单的实现
- [ ] **效率**：有没有明显的性能问题（N+1、不必要的循环）
- [ ] **安全**：有没有注入、硬编码密钥、不安全反序列化
- [ ] **可读**：别人能否在 5 分钟内读懂

### 根因优先（来自 `.agent/standards/delivery.md`，**评审时优先判断**）

在解决问题或修复 Bug 时，必须定位并消除**根本原因**，而不是只压制表面症状、绕过触发条件或堆叠局部补丁。

按以下顺序处理：

1. **复现并描述**：说明在什么输入、状态或条件下出错，以及预期行为与实际行为的差异。
2. **定位根因**：沿调用链、数据流或状态变化追踪到最上游的缺陷来源，**不**停留在最先报错或最显眼的位置。
3. **判断影响面**：确认该根因是否同时影响其他路径、模块、数据或接口，避免只修一处而留下同类隐患。
4. **从源头修复**：修改引发问题的代码、数据或设计，使问题在同类场景下不再发生，而不只是让当前症状消失。
5. **回归验证**：为根因补强或新增测试，防止同类问题再次出现。

**打补丁的反例**（仅当无法从根源修复时才允许，必须记录原因与临时缓解措施，并登记后续根治任务）：

- 屏蔽异常（`except: pass` / 静默吞错）
- 特判某个输入绕过失败路径
- 在调用方补 `if not None` 让代码「看起来能跑」
- 加日志后忽略错误

**评审打补丁检测**：

- [ ] 修复 commit 是否包含「失败原因分析 / 调用链追踪 / 同类场景回归测试」？
- [ ] 是否只修了当前报错路径而留下其他同类隐患？
- [ ] 是否有同类型 bug 的历史记录（如 `memory/funclip-*.md` 中提及）？如果同类问题 2 次以上，必须从根因修复。

### 评审后处理

- [ ] 发现的**确认问题**已修
- [ ] **不确定问题**已讨论或显式 defer
- [ ] **虚假警报**已排除
- [ ] fixup commit 已 squash（保持线性历史）

### 自查（提交前最后一遍）

- [ ] git diff 与设计一致
- [ ] 没有忘记的文件
- [ ] 没有遗留的 TODO / FIXME
- [ ] CI 全绿（如果有）

## 出口条件

- [ ] 评审通过（或显式接受已知缺陷）
- [ ] 所有「必查项」都检查过
- [ ] 修复 commit 已通过「根因优先」5 步检查

## 反例

- ❌ 评审只是"看上去 OK"就过了
- ❌ 把"我觉得没问题"作为评审理由
- ❌ 评审完不修问题就合并
- ❌ 只改当前报错路径，不问"同类场景会怎样"
- ❌ 用 `try/except` 吞掉错误让测试通过，不追根因
