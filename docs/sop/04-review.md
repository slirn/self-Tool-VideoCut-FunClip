# 阶段 4：评审

**目标**：在合并前发现缺陷，确保代码质量。

## 入口条件

- 实现已提交（git log 可见）
- 自测通过

## 产出

- `code-review` 报告（用 `/code-review` skill）
- 评审后的 commit（fixup）

## Checklist

### 评审维度

用 `/code-review <effort>` 跑评审，effort 级别：

| 级别 | 适用 | 产出 |
|---|---|---|
| `low` | 改 < 50 行、改动局限 | 少量高置信度发现 |
| `medium` | 改 50-200 行、跨模块 | 标准发现 |
| `high` | 改 > 200 行、新功能 | 全面发现，可能含不确定项 |
| `max` | 架构变更、核心模块 | 全部维度 |

### 必查项

- [ ] **正确性**：实现是否真满足验收标准
- [ ] **简化**：有没有可以更简单的实现
- [ ] **效率**：有没有明显的性能问题（N+1、不必要的循环）
- [ ] **安全**：有没有注入、硬编码密钥、不安全反序列化
- [ ] **可读**：别人能否在 5 分钟内读懂

### 评审后处理

- [ ] 发现的**确认问题**已修
- [ ] **不确定问题**已讨论或显式 defer
- [ ] **虚假警报**已排除
- [ ] fixup commit 已 squash（保持线性历史）

### 自查（提交前最后一遍）

- [ ] git diff 与设计一致
- [ ] 没有忘记的文件
- [ ] 没有遗留的 TODO / FIXME
- [ ] CI 全绿（如果有）

## 出口条件

- [ ] 评审通过（或显式接受已知缺陷）
- [ ] 所有"必查项"都检查过

## 反例

- ❌ 评审只是"看上去 OK"就过了
- ❌ 把"我觉得没问题"作为评审理由
- ❌ 评审完不修问题就合并
