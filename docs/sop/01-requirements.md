# 阶段 1：需求澄清

**目标**：把"用户想法"变成"可执行的需求清单"，每条都有可验证的验收标准。

> 公共规范 `collaboration.md` 与本 SOP 等价（`adopt` 关系），完整协作规则见 `.agent/standards/collaboration.md`。本节末「信息分类标签」是公共规范的最小子集。

## 入口条件

- 用户有明确要解决的问题，或
- 上游 issue / 反馈 / 内部需求

## 产出

`docs/REQM/REQ-<id>.md`（id 用 YYYYMMDD-NNN 格式，**实际存储在 `docs/REQM/`，与 SOP 历史模板的 `requirements/` 路径不一致**——已登记为 `legacy-gap`）

## Checklist

### 业务层

- [ ] 一句话讲清楚**解决什么问题**（不写技术方案）
- [ ] 标注**优先级**（P0 必做 / P1 应做 / P2 后续）
- [ ] 列出**不做的事**（anti-examples）

### 用户故事 / 用例

- [ ] 至少 1 个典型使用场景
- [ ] 描述**谁**、**在什么条件**下、**做什么**、**看到什么结果**
- [ ] 至少 1 个**异常场景**（错误输入、边界条件）

### 验收标准（关键）

每条标准必须满足：
- [ ] 具体（不是"用户体验好"，而是"加载时间 < 2s"）
- [ ] 可验证（"输入 X，输出 Y"）
- [ ] 独立（一条标准只测一件事）

### 技术约束

- [ ] 依赖（要用的库/模型/API）
- [ ] 性能/资源约束（启动时间、内存、文件大小）
- [ ] 兼容性要求（Python 版本、操作系统）

### 完整性自检

- [ ] 如果让一个不了解项目的工程师看这份文档，他能直接判断"完成 vs 没完成"
- [ ] 所有术语有定义或链接到参考资料

### 信息分类标签（与 `.agent/standards/collaboration.md` 对齐）

每条事实 / 假设 / 建议必须明确标注以下标签之一（不能省略）：

| 标签 | 含义 | 示例 |
| --- | --- | --- |
| `[已确认]` | 用户明确确认的需求，或有依据的现状事实 | `[已确认] 精剪输出分辨率支持 720p / 1080p / 原始` |
| `[待确认]` | 可能影响结果 / 范围 / 行为的假设 | `[待确认] 用户是否需要在精剪完成后自动生成 SRT 字幕？` |
| `[建议]` | Agent 推荐但尚未获批的选项 | `[建议] 输出文件名带时间戳避免覆盖` |
| `[可自主决定]` | 已授权范围内、低风险、可逆的实现细节 | `[可自主决定] 临时调试日志写到 console 还是文件` |

**关键原则**（来自 `collaboration.md`）：
- 事实尽可能给出代码、配置或文档依据
- 重大假设未确认前，不得实施依赖它的修改
- 沉默不视为批准；确认目标不等于批准全部技术细节

## 出口条件

- [ ] 用户（或代理）确认需求清单无歧义
- [ ] 验收标准全部是"能跑测试验证"的，不是主观判断
- [ ] 所有 `[待确认]` 项已与用户确认或显式 defer
- [ ] 所有 `[建议]` 项已获批或显式 reject

## 反例（不该出现在需求文档里）

- ❌ "界面要美观" → 应改成"按钮颜色与品牌色 #XXXXXX 一致"
- ❌ "运行要快" → 应改成"100MB 视频识别 < 5 分钟"
- ❌ "支持多语言" → 应改成"支持 zh/en/ja 三种语言，模型自动选择"
- ❌ 把所有事实 / 假设 / 建议混在一起，不标 `[已确认]/[待确认]/[建议]` → 读者无法区分已批准与待决策内容
