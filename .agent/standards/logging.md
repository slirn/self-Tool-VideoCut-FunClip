# 统一日志与流程追踪规范

## 目的与适用范围

业务项目需要定位问题、观察端到端流程或展示执行节点时，必须使用统一日志模块。各程序可以按需要插入日志，但不得直接操作日志表、各自定义持久化格式或绕过统一开关。本规范定义能力和边界，具体数据库、框架和页面技术由项目上下文决定。

## 核心能力

统一日志模块至少提供以下能力：

- 统一调用入口，例如 `log(event)`、`startFlow`、`endFlow` 和异常记录接口；
- 运行时总开关，可关闭或打开日志持久化；
- 按环境、模块、日志级别或流程类型的细粒度开关；
- 日志写入数据库，并包含结构化字段，不依赖拼接文本才能查询；
- 将同一请求、任务、会话或业务流程的日志关联为可追踪链路；
- 页面查询和流程展示，能够按时间、流程、关联 ID、模块、节点、级别和结果筛选，并按顺序查看节点详情；
- 记录日志失败时不应破坏主业务流程，除非项目明确将审计日志定义为强一致要求；
- 开发环境默认可以打开详细日志，生产环境默认遵循项目安全和性能策略。

## 日志开关

开关状态必须有明确来源、优先级和审计规则。至少区分：

1. 系统总开关：控制是否持久化普通诊断日志；
2. 模块或程序开关：控制指定模块是否产生日志；
3. 级别开关：控制 DEBUG、INFO、WARN、ERROR 等级别；
4. 流程追踪开关：控制是否记录流程节点和链路详情。

关闭日志后，业务代码仍可调用统一日志入口，但模块应快速返回，避免构造昂贵的调试数据。ERROR、安全事件或项目规定的审计日志是否仍然记录，必须在项目上下文中明确，不能由实现者猜测。开关变更应记录操作者、时间、旧值、新值和原因；修改开关需要权限控制。

## 结构化数据模型

日志记录至少应支持以下字段或等价字段：

- 发生时间、级别、环境、应用/模块、程序或类、事件名称；
- 流程 ID、请求 ID、任务 ID、会话 ID、业务对象 ID 等关联标识；
- 节点名称、节点序号、开始/结束时间、耗时、状态和错误分类；
- 方法/函数名称、所属模块、调用开始时间、执行耗时和慢调用标记（需要方法级性能定位时）；
- 简短消息、结构化上下文、异常摘要和可选堆栈；
- 操作者或调用来源（按项目权限模型处理）；
- 日志版本、采样标识和保留/清理状态（适用时）。

结构化上下文必须可被安全序列化和查询。禁止把密钥、令牌、密码、完整支付信息、个人敏感信息或未经脱敏的请求体直接写入日志。项目必须定义字段脱敏、最大长度、保留期限、归档和删除策略。

## 统一日志事件契约

不同应用必须通过统一的事件契约提交日志，不得让每个系统自行设计一套调用参数。各语言可提供本地 SDK、适配器或包装器，但最终提交到日志平台的字段名称、语义和层级保持一致；业务差异放入可扩展的结构化 input 和 output 对象中。

推荐统一调用签名：

log({ eventType, eventName, level, source, method, flow, input, output, result, error, timing, context })

固定顶层参数及含义：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| eventType | string | 是 | 事件类型，如 method、node、flow、external_call |
| eventName | string | 是 | 稳定的业务事件名称，不使用易变的源代码行号 |
| level | enum | 是 | DEBUG、INFO、WARN、ERROR 或项目定义的级别 |
| source | object | 是 | 应用、服务、模块、版本和环境等来源信息 |
| method | object/null | 否 | 类/函数名称及方法级调用信息 |
| flow | object/null | 否 | 流程、请求、任务、会话、父节点和节点序号等关联信息 |
| input | object/null | 否 | 方法或节点的输入参数；由应用定义字段，但必须结构化和脱敏 |
| output | object/null | 否 | 方法或节点的输出结果；由应用定义字段，但必须结构化和脱敏 |
| result | object | 是 | status、业务结果码和摘要消息等统一结果信息 |
| error | object/null | 否 | 错误类型、错误码、摘要和受控堆栈信息 |
| timing | object | 是 | 开始时间、结束时间、耗时毫秒数和慢调用标记 |
| context | object | 否 | 可扩展的业务上下文；不得用来替代固定字段 |

input 和 output 的顶层结构固定为对象或 null，内部字段由各应用根据业务定义。应用必须为自身 input/output 提供版本或 schema 标识，以便平台解释数据；禁止把整个请求或响应未经筛选地直接塞入对象。没有输入或输出时使用 null，不使用不一致的空字符串、数组或自定义字段名。

应用系统负责实现本系统的日志接口适配器：将本地参数映射到上述固定契约、补齐来源和关联信息、执行脱敏/截断、计算耗时并提交给统一日志模块。日志平台只依赖统一字段展示和查询，不依赖某个业务系统的内部对象名称。平台应保留未知扩展字段，不能因不同应用的 input/output 内容不同而丢弃事件。

固定契约的兼容规则：新增可选字段不应破坏旧消费者；修改字段语义或必填性必须提升契约版本；删除或重命名字段需要迁移方案。应用不能通过 context 绕过固定的 source、flow、result 或 timing 字段。
## UML 时序图与日志节点映射

统一日志平台应支持标准 UML 时序图作为流程理解入口。应用系统可以根据实际业务流程生成 UML 时序图，平台加载时序图和日志事件后，使用稳定的调用标识将两者关联；不应仅使用方法名、显示名称或源代码行号作为映射键。

### 统一调用标识

每个时序图中的调用节点必须有稳定的 callId。日志事件在 flow 中使用相同的 callId，并可补充 callInstanceId 区分同一调用在重试、循环或并发场景下的具体实例。推荐字段：

| 字段 | 位置 | 说明 |
| --- | --- | --- |
| callId | 时序图调用节点、日志 flow | 稳定的业务调用标识，跨图和日志一致 |
| callInstanceId | 日志 flow | 一次实际执行实例的标识，用于重试、循环和并发调用 |
| diagramId | 时序图元数据、日志 flow | 所属时序图标识 |
| diagramVersion | 时序图元数据、日志 flow | 图版本，避免图变更后错误映射 |
| sourceParticipant | 时序图调用节点 | 发起方参与者 |
| targetParticipant | 时序图调用节点 | 被调用方参与者 |
| operation | 时序图调用节点、日志 method/eventName | 调用操作名称 |

应用的日志适配器负责把本地调用上下文映射为 callId、callInstanceId、diagramId 和 diagramVersion。日志平台必须保留这些字段，即使时序图暂时不可用，也不能丢弃日志。

### 时序图格式与生成

参考平台应优先支持 Mermaid sequenceDiagram 或等价的标准化结构，并保留原始图文本/模型及解析后的节点数据。应用可以手工维护、由代码注解生成或根据实际调用配置生成时序图，但生成结果必须为每个可追踪调用节点提供 callId。图中参与者、调用方向、返回、分支、循环和异常路径应能被解析或明确标注。

平台生成日志流程展示时，应以时序图定义的参与者和调用关系为骨架，再填充实际日志中的状态、耗时、输入、输出和错误信息。没有匹配日志的调用节点显示为未执行或无数据；有日志但没有图节点的事件显示为未映射，并提供告警，不能静默丢失。

### 双向跳转

- 点击时序图调用节点：根据 callId、callInstanceId 和图版本定位日志节点，并滚动画布、聚焦和突出对应日志卡片；若有多个实例，先展示实例选择或按时间定位。
- 点击日志节点：根据同一组标识反向定位时序图调用节点，滚动到该节点并突出显示；图中不存在时显示未映射原因。
- 跳转不得只依赖颜色或瞬时选中状态，目标节点应有明确的焦点标记，并保留当前流程、过滤条件和返回路径。
- URL 或页面状态应可表达当前 diagramId、callId、callInstanceId 和 flowId，便于复制链接和恢复定位。

## UML 时序图与日志验收

至少验证：

- 应用提供的时序图可以加载并展示参与者、调用方向、返回和关键分支；
- 时序图调用节点与日志事件通过相同 callId 正确关联，图版本不匹配时明确提示；
- 点击时序图节点可以定位并突出对应日志节点；
- 点击日志节点可以反向定位并突出时序图节点；
- 同一调用的重试、循环和并发实例通过 callInstanceId 正确区分；
- 无匹配日志或无匹配图节点时均有明确状态和原因，不静默丢失；
- 时序图和日志卡片展示的输入、输出、状态、耗时和异常信息保持一致；
- 跳转状态可通过 URL 或页面状态恢复。
## 流程与节点追踪

需要展示流程时，调用方应显式创建或继承流程上下文，并在关键节点记录开始、成功、失败、跳过和重试事件。节点应使用稳定名称，不得只依赖源代码行号。异步任务、队列消费、定时任务和跨服务调用必须按项目约定传递关联 ID；跨边界丢失链路时，应记录原因。

页面展示至少包括流程列表、流程详情、按时间排序的节点时间线、节点状态/耗时、失败节点及异常摘要和关联日志筛选。页面应分页或限制查询范围，默认避免一次加载全部日志。查看日志需要权限控制，并对敏感字段继续脱敏。

统一日志平台的流程详情优先使用流程图画布或等价的节点卡片视图，不以传统日志列表作为主要展现方式。节点按执行关系连接，分支、重试、跳过和失败路径应能区分。每个节点默认展示完整的核心日志信息，包括节点名称、模块/方法、开始时间、结束时间、耗时、状态、慢调用标记、消息、结构化上下文、异常摘要和关联 ID；较长内容应在卡片内换行或展开，不得默认截断关键字段。

画布应支持缩放、平移、适配全流程和长流程导航；节点卡片保持稳定且可读的宽度。慢调用、失败和重试必须同时使用文字、图标或边框等非颜色标识突出显示。实现可以使用 React Flow 等成熟流程画布组件，但具体前端技术由项目上下文决定。

## 方法耗时与慢调用

在启用方法级诊断或性能追踪时，统一日志模块必须能够记录被监测方法的名称、所属模块、调用开始时间、执行耗时和执行结果。耗时使用单调时钟或等价的可靠计时来源计算，避免系统时钟调整造成错误时长。同步方法应在调用结束时记录总耗时；异步方法应覆盖实际异步工作完成时间，而不是只记录返回 Future/Promise 的时间。异常退出的方法也必须记录耗时和失败结果。

单次方法调用耗时 **超过 1000 毫秒（1 秒）** 时，标记为慢调用，并在数据库结构化记录和诊断页面中突出显示；恰好 1000 毫秒不属于“超过 1 秒”，除非项目另行配置阈值。突出显示至少包括清晰的慢调用标识和可排序/筛选的耗时，不能只依赖颜色区分。阈值应集中配置，默认值为 1000 毫秒。

方法耗时采集应受总开关和方法级/模块级追踪开关控制。自动埋点或包装器可以用于广覆盖，关键热点和业务节点也可以显式插入统一计时调用；不得对每个方法无条件进行高开销数据库同步写入。采样、批量或异步写入等优化不得导致慢调用标记的判定逻辑失效，并应测量日志采集本身的开销。

## 调用约定

业务程序可以在任何需要定位问题的位置插入日志，但只能依赖统一日志接口。插入日志前应说明事件的业务意义、级别和关联上下文；不要在循环中无界写入，也不要为同一事件重复记录。推荐记录：入口、外部调用、关键状态转换、重要分支、重试、异常和流程结束。

日志模块应支持延迟构造或等价机制，使关闭日志时不计算昂贵上下文。数据库写入应采用批量、异步或项目适用的可靠机制，并明确丢弃、重试和降级策略。

## 验收要求

至少验证：

- 总开关关闭时，业务仍正常运行，普通日志不写入数据库；
- 打开总开关或目标模块开关后，插入点产生可查询的结构化记录；
- 同一流程的请求、任务或会话可以关联并按时间展示；
- 成功、失败、重试、跳过和异常节点状态正确；
- 页面以流程画布或完整节点卡片作为主要视图，节点核心日志无需逐个点击即可阅读；
- 画布支持流程连接、分支/重试/失败路径、缩放、平移和适配全流程，长流程下卡片仍可读；
- 节点卡片展示完整核心日志信息，长文本可换行或展开；
- 页面支持筛选、分页、详情查看和权限控制；
- 日志数据库不可用、写入超时或日志量增大时，主业务符合项目定义的降级策略；
- 方法成功、异常和异步完成路径均记录正确耗时；
- 耗时大于 1000 毫秒的方法被标记并在页面突出显示，1000 毫秒边界行为符合定义；
- 慢调用可按方法、模块、时间和耗时筛选/排序，且计时开销符合项目性能预算；
- 敏感信息不会以明文进入数据库、页面、导出文件或错误响应；
- 开关变更可追溯，且未授权用户不能修改或查看受限日志。

实现统一日志模块时，计划必须单独列出：日志库/表与迁移、统一 API、开关配置、流程关联、流程画布/节点卡片展示、页面查询展示、方法耗时采集、1000 毫秒慢调用标记、权限脱敏、保留清理和测试验证。
