# 分阶段交付规范

## 风险分级

- 低风险：文案、格式、明确且局部的修复，可直接执行并验证。
- 一般任务：新功能、一般重构，必须经过需求确认、方案确认、最小切片实现和验收。
- 高风险：数据迁移/删除、权限、安全、外部 API 兼容、基础设施、显著成本或难回滚变更，必须说明影响、验证和回滚，并获得明确批准。

## 阶段一：需求确认

先输出“需求确认卡”：

1. 目标和用户可观察结果；
2. 本次不做什么；
3. 已确认事实和待确认假设；
4. 正常、失败、边界、权限、兼容性场景；
5. 需要用户回答的问题。

新增功能或行为不明确时，确认前不得开始功能实现。允许只读调查，但要说明尚未确定的事项。

## 阶段二：方案确认

只输出：推荐方案、影响模块、核心流程、关键取舍、风险、第一个可验收切片和需批准事项。默认不展开到函数、类和逐文件设计。影响业务行为、兼容性、成本、安全或数据的取舍必须显式确认。方案确认时先核对已验证模式清单（见「复用优先」），命中即复用。

## 阶段三：最小切片

切片应能独立验证用户结果，而不只是按数据库、后端、前端分层。每个切片说明可观察结果、修改边界、验证方式和未包含能力。优先实现验证核心假设的最小闭环。不得为了“顺便优化”扩大范围。

## 阶段四：验收

按验收标准逐项汇报：

| 验收项 | 验证方式或证据 | 结果 |
| --- | --- | --- |
| 具体行为 | 测试、演示或检查记录 | 通过 / 失败 / 未验证 |

区分“代码已实现”“自动验证已通过”和“用户已验收”。未运行的测试不得写成通过。

## 功能点清单（进度出口）

功能模块开发开始前，先列出该模块**全部功能点**，形成一份独立的简洁清单文档（建议 `docs/manual/<module>-checklist.md`，与使用说明书相邻）。用户通过这一份文档即可查看模块整体进度，不需要翻阅其他材料。

- **先列全、后开发**：清单在开发前列出全部功能点，每点一行、带稳定编号；开发中途新增功能点时追加并标注，不删除、不改写已有点。
- **完成即标记**：功能点测试通过并同步使用说明书后，立即在清单中打完成标记并记录完成时间；只允许标记已通过验证的功能点，进行中的不打标。
- **双向可达**：每个功能点链接到使用说明书对应说明章节，说明书章节回链清单条目；用户从任一文档都能跳到另一文档的对应位置。
- **边界**：功能点清单面向用户展示功能进度，不替代 `orchestration.md` 的执行任务清单与状态记录，两者不互相覆盖。

## 功能使用说明书（用户反馈出口）

AI 执行的设计、开发、测试过程对用户不可见。为让用户及时看到最新开发结果，每个功能模块**每完成一部分功能（切片测试通过）都必须同步编写或更新图文使用说明书**；说明书未更新的部分视为未完成。

- **位置与对应**：每个功能模块一份，放在业务项目固定目录（如 `docs/manual/<module>.md`），与代码同一提交入库；说明书章节与功能切片一一对应，可对照变更记录追溯每部分的完成状态。
- **图文结合**：界面功能配操作过程与结果截图；无界面的功能配调用示例、流程图或时序图。图必须取自真实测试运行过程，不得臆造；文字说明操作步骤、预期结果与已知限制。
- **内容要素**：功能用途与入口、逐步操作说明（配图）、预期结果（配图）、异常与提示说明、已知问题与未包含能力。
- **时机**：该部分功能测试通过后立即编写或更新，随切片同提交；阶段四验收时用户以说明书对照实际运行结果逐项确认。
- **面向用户**：说明书写给最终使用者，不写实现细节、内部结构与代码位置。

## 复用优先

实现前先查项目的已验证模式清单：认证与授权、分页与查询、错误码与异常、日志埋点、配置读取、数据访问等常见问题若已有验证过的实现，必须复用，不得重新发明。偏离清单选择新方案时，须在方案确认阶段说明理由并获确认。

- 模式清单按 `knowledge-placement.md` 作为项目知识维护，每条记录适用场景、参考实现位置、验证证据和已知限制；
- 新模式必须经过一次完整交付（含验收证据）才能入库，未经交付验证的做法不得登记为已验证模式；
- 复用是指向同一实现或经认可的封装，不是把相似代码复制到多处；发现清单外的重复实现时按 `technical-debt.md` 登记，不在当前任务中顺手重构。

## 编码统一 UTF-8

所有新建或修改的文件——源代码、文档、配置、模板、脚本、日志与生成内容——一律使用 UTF-8 编码（推荐无 BOM），禁止 GBK/GB2312、UTF-16 等其他编码混入仓库。

- 工具与脚本写文件时必须显式指定 UTF-8（如 PowerShell 的 `-Encoding utf8`、Node 的 `'utf8'`），不依赖平台默认值；Windows 环境尤须注意 cmd 与 PowerShell 的默认编码差异；
- 仓库中已有的非 UTF-8 文件：本次任务触及该文件时一并转存为 UTF-8；未触及的不做顺手批量转换；
- 外部工具链强制要求其他编码时，在项目上下文登记例外与原因，不静默混用；
- 验收时中文出现乱码一律视为编码缺陷，不得以“显示问题”解释为通过。

## 根因优先

在解决问题或修复 Bug 时，必须定位并消除引发问题的根本原因，而不是只压制表面症状、绕过触发条件或堆叠局部补丁。

按以下顺序处理：

1. 复现并描述：说明在什么输入、状态或条件下出错，以及预期行为与实际行为的差异。
2. 定位根因：沿调用链、数据流或状态变化追踪到最上游的缺陷来源，不停留在最先报错或最显眼的位置。
3. 判断影响面：确认该根因是否同时影响其他路径、模块、数据或接口，避免只修一处而留下同类隐患。
4. 从源头修复：修改引发问题的代码、数据或设计，使问题在同类场景下不再发生，而不只是让当前症状消失。
5. 回归验证：为根因补强或新增测试，防止同类问题再次出现。

打补丁是指只处理报错表象（如屏蔽异常、特判某个输入、绕过失败路径、吞掉错误），而不消除真正的缺陷来源。这类修复仅当无法从根源修复时才允许，且必须记录原因与临时缓解措施，并登记后续根治任务。
