# 架构 Fitness 与演进规范

## 目的

本规范用于把架构边界、依赖方向和质量属性转化为持续检查的 fitness function，避免架构只存在于文档中而在代码演进中逐步失效。

## 基本原则

- 架构规则必须可执行、可诊断，并有明确负责人。
- 规则覆盖模块依赖、数据所有权、接口边界、循环依赖和资源约束。
- 新增例外必须有理由、范围、负责人和到期时间。
- ADR 记录重要决策，fitness function 验证决策是否仍被遵守。
- 规则应聚焦少量关键边界，不对所有实现细节过度约束。

## 必须定义的架构边界

项目至少明确适用的：

- 分层和模块依赖方向；
- 领域、应用、基础设施和接口层边界；
- 公共 API 与内部实现边界；
- 数据所有权和跨模块数据访问限制；
- 同步、异步、事件和队列边界；
- 外部系统适配边界；
- 共享库和平台代码边界；
- 禁止依赖、循环依赖和反向依赖。

## 规则即代码

架构规则应使用 YAML、JSON 或项目已有工具配置。公共规则至少支持：

```text
required-files
forbidden-files
max-file-lines
forbidden-imports
layer-dependencies
```

规则必须输出：

- 规则 ID；
- 文件位置；
- 实际依赖或违规值；
- 期望约束；
- 修复建议。

## 循环依赖

公共模块、领域模块和共享库不得形成循环依赖。发现循环时：

1. 确认是否属于同一领域边界；
2. 提取稳定接口或事件；
3. 调整依赖方向；
4. 必要时建立迁移切片和临时例外；
5. 增加回归检查。

不得通过动态导入、字符串反射或聚合入口永久隐藏循环依赖。

## 数据所有权

- 每个数据实体有明确所有者模块。
- 其他模块通过公开接口或事件访问数据，不直接读取内部表或本地文件。
- 跨模块事务必须明确一致性策略。
- 数据库、缓存、搜索索引和数据仓库的写入责任必须唯一或明确协调。
- 数据迁移必须保留兼容和回滚路径。

## 架构演进

- 新功能优先建立在已批准边界内。
- 新边界或跨模块依赖需要 ADR 或设计说明。
- 大规模重构应按可验证切片迁移。
- 旧规则在新架构完成迁移前保留兼容检查。
- 规则变化必须更新 ADR、架构文档和例外清单。

## 例外

例外必须记录：

- 违反的规则；
- 受影响模块和文件；
- 业务或迁移原因；
- 风险和补偿措施；
- 负责人；
- 到期时间和退出条件。

安全、数据隔离和核心依赖方向不得使用永久例外。

## 验收

- 核心边界有可执行规则；
- CI 或本地检查能够阻止新增违规；
- 规则输出位置和修复方向清晰；
- 循环依赖、反向依赖和内部数据访问被检测；
- ADR 与当前规则一致；
- 例外可到期、可审计，并有关闭证据。
