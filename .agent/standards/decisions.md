# 工程决策记录规范

## 目的

本规范用于保留重要工程决策的背景、取舍和后果，避免后续人员只看到结果而不知道原因，反复推翻已有决策或在不知情下破坏约束。

本规范不要求把普通实现细节写成文档。

## 必须记录的决策

出现以下情况时必须建立决策记录：

- 影响多个模块、服务、仓库或团队；
- 涉及数据模型、公共契约、权限、安全或基础设施；
- 难以回滚或迁移成本较高；
- 存在多个合理方案并进行了重要取舍；
- 有意偏离公共规范或项目既有规则；
- 同一问题反复讨论且没有稳定结论。

局部、低风险且容易撤销的实现选择继续记录在任务简报中，不单独建立记录。

## 最小记录格式

决策记录至少包含：

| 字段 | 内容 |
| --- | --- |
| 标题 | 简短表达决定，不使用“方案讨论”等模糊名称 |
| 状态 | `proposed`、`accepted`、`superseded` 或 `deprecated` |
| 日期 | 决策日期 |
| 负责人 | 对结果负责的人或角色 |
| 背景 | 要解决的问题和当前约束 |
| 决策 | 最终选择及其边界 |
| 备选方案 | 考虑过的其他方案 |
| 后果 | 收益、成本、风险和需要接受的取舍 |
| 证据 | 验证、评审、原型或数据依据 |
| 复核条件 | 何时需要重新评估 |

模板见 `templates/decision-record.md`。

## 记录位置与生命周期

业务项目应把决策记录放在稳定目录，例如：

```text
docs/decisions/
0001-use-event-driven-inventory-sync.md
```

项目已有决策目录时沿用项目结构。决策记录一旦接受，不应通过直接改写历史来改变含义；需要改变决定时，创建新记录并把旧记录标记为 `superseded`。

需要修改已接受决策但尚未产生新决定时，状态保持 `proposed` 或明确标记为“待复核”，不得让 Agent 静默覆盖。

## 与任务和规范的关系

- 任务简报只记录当前任务相关决策摘要，并链接正式决策记录。
- 项目上下文记录稳定事实和约束，不替代决策背景。
- 项目规范适配表记录偏离关系，决策记录解释为什么选择该偏离。
- 决策影响公共规范时，应按 `adoption.md` 评估是否需要回到公共规范仓库。

## 验收

- 重要决策可以从项目入口或项目上下文找到；
- 决策包含背景、取舍和后果；
- 被替代的决策保留历史并能追溯原因；
- 普通实现细节没有被过度文档化。
