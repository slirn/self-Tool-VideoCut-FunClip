# 发布与来源追溯规范

## 目的

本规范确保任何已安装、已构建或已发布的版本都能回答三个问题：

1. 它是什么版本；
2. 它来自哪个提交；
3. 如何重新构建同样的产物。

版本名称只是人类可读标识，完整提交和产物信息才是追溯依据。

## 版本标识

正式发布必须使用不可变的 Git tag。推荐使用 annotated 或 signed tag。

正式版本不得只使用以下内容作为来源标识：

- 分支名称；
- 本地工作区目录；
- 人工传入但未校验的版本字符串；
- 未记录提交的构建产物。

版本号可以选择 SemVer 或项目已确认的方案，但同一项目必须保持一致。破坏兼容性的变更必须按照项目兼容策略提升主版本或提供迁移期。

## 发布前置条件

- 工作区干净，没有未提交的发布内容；
- tag 已存在并指向预期提交；
- tag 对应的代码已通过质量门禁；
- 依赖锁定文件已提交；
- 构建环境、工具链和关键配置已记录；
- 数据库迁移、兼容性和回滚方案已验证。

## 必须记录的信息

每次正式发布至少记录：

| 字段 | 含义 |
| --- | --- |
| `version` | 人类可读版本号 |
| `sourceCommit` | 完整 Git 提交哈希 |
| `tag` | 与提交对应的正式 tag |
| `artifact` | 包、镜像或部署产物标识 |
| `artifactDigest` | 产物摘要、镜像 digest 或等价校验值 |
| `builtAt` | 构建时间及适用时区 |
| `toolchain` | 编译器、运行时、包管理器或关键构建工具版本 |
| `changes` | 变更记录或发布说明 |
| `verification` | 质量门禁和发布验证结果 |

项目和 Agent 不得用短期分支名或“最新版本”替代上述来源信息。

## 可复现与产物

- 构建必须从已提交内容开始，不依赖未记录的本机文件。
- 构建脚本、锁文件和依赖来源必须可追溯。
- 同一提交在相同工具链下应生成等价产物；无法完全复现时必须记录不可复现原因。
- 业务工程安装依赖时，锁文件应记录版本和来源提交。
- 容器镜像应优先使用 digest，不只记录可变 tag。

是否生成 SBOM、签名或证明材料由组织策略决定；一旦采用，产物必须与具体版本和提交关联。

## 发布验证

发布前和发布后至少验证：

- tag 指向的提交与构建输入一致；
- 产物摘要可读取且与发布记录一致；
- 业务工程能够从正式 tag 或发布产物获取相同内容；
- 安装锁文件能够还原相同版本；
- 回滚到上一版本时，代码、数据和配置兼容。

## 例外

无法创建正式 tag 时，只能作为临时预发布处理，必须记录：

- 临时提交哈希；
- 未创建 tag 的原因；
- 使用者范围；
- 正式版本替换时间和负责人。

不得把临时提交长期标记为正式版本。

## 验收

- 每个正式版本可从 tag 定位到完整提交；
- 构建和安装记录包含版本、提交和产物摘要；
- 发布产物可从记录的信息重新获取或重建；
- 没有名义版本与实际来源不一致的情况。
