# 任务受理与用户协作规范

## 目的

本规范统一用户向 Agent 提交任务的入口规则：用户输入不要求完整周全，Agent 按受理模板校验、集中询问补齐，补齐并确认后才作为已受理需求进入交付流程；同时明确用户在各流程节点的操作规则，降低用户的记忆和表述负担。

## 基本原则

- 用户输入可以不完整，但必须真实；完整性由 Agent 通过询问补齐，不依赖用户事先考虑周全。
- 受理是显式动作：达到受理模板要求并经用户确认后，任务才进入 `delivery.md` 阶段一。
- 先查后问：能从工程、文档和历史记录查明的事实不问用户。
- 集中少量提问：每次最多 3 个影响目标、范围或验收的问题，附选项和建议。
- 用户回答按信息分类标注（`[已确认]` / `[待确认]` / `[建议]` / `[可自主决定]`），与 `collaboration.md` 一致。
- 用户明示"由你决定"的字段标 `[可自主决定]`，不重复询问。

## 受理模板

受理卡按任务类型必填以下内容；缺失项由 Agent 询问补齐：

### 通用必填

| 字段 | 要求 |
| --- | --- |
| 任务类型 | 新需求 / Bug 修复 / 文档任务 / 多任务计划 |
| 目标与可观察结果 | 一句话目标；完成后用户能看到什么 |
| 不做什么 | 排除项；缺失时 Agent 给默认建议供确认 |
| 风险初判 | 低 / 一般 / 高（按 `delivery.md` 分级），方案阶段复核 |
| 验收标准 | 每条可验证（"输入 X、操作 Y、输出 Z"）；Agent 起草，用户确认 |
| 已知事实与假设 | 用户提供的标注 `[已确认]` 或 `[待确认]` |

### 按类型追加

| 类型 | 追加必填 |
| --- | --- |
| 新需求 | 典型使用场景；异常或边界场景；优先级；技术约束（依赖、性能、兼容） |
| Bug 修复 | 复现步骤；预期行为；实际行为；环境与版本；出现频率和影响范围（是否回归） |
| 文档任务 | 文档类型与受众；落盘位置（按 `knowledge-placement.md` 进仓库）；现状缺口；验收 = 逐条可核对的内容点 |
| 多任务计划 | 转 `orchestration.md` 阶段一建计划，逐项引用本模板 |

## 询问补齐流程

```text
用户提出任务
-> Agent 只读调查（查工程事实，能自答的不问）
-> 对照受理模板列出缺失项，筛选影响目标、范围或验收的问题
-> 集中询问（每次最多 3 个，附选项和建议）
-> Agent 补全受理卡并标注信息分类
-> 向用户复述受理卡（目标 / 范围 / 验收 / 风险级）
-> 用户确认 -> 进入 delivery.md 交付流程
```

- 用户暂无法回答关键项时，任务停留在受理阶段，不得带未确认假设实施；可先执行不依赖缺失项的部分并说明。
- 受理卡和用户问答记录写入项目流程规定的目录（如 `docs/REQM/`、`.agent/tasks/`），位置记录在 `.agent/project-context.md`，随仓库版本管理。
- 低风险任务（文案、格式、明确的局部修复）：Agent 可按模板代填默认值并标 `[可自主决定]`，执行前一句话复述即可，不强制完整询问。

## 用户操作规则

| 流程节点 | 用户要做的 |
| --- | --- |
| 提任务 | 按受理模板尽量说全五要素；说不全没关系，等 Agent 集中询问 |
| 需求确认卡 | 回答卡上问题（每次最多 3 个）；确认或纠正范围 |
| 方案确认卡 | 批准时说清本次批了什么、没批什么；沉默不视为批准 |
| 连续执行 | 多任务一次批准计划；范围外发现单独提出，不"顺便"加 |
| 验收 | 盯证据不盯描述；区分"已实现 / 自动验证通过 / 已验收"三层 |
| 纠偏 | 说"不是我想要的"时讲清预期与实际的差异，Agent 先改验收标准再给最小纠偏方案 |
| 高风险操作 | 数据、权限、安全、外部兼容、基础设施变更逐次单独批准 |

## 验收

- 进入执行的任务均有达到受理模板要求的受理记录，且位于仓库内；
- 影响目标、范围或验收的缺失项经过询问补齐，未靠假设填补；
- 每次询问不超过 3 个问题，且未询问工程可查明信息；
- 用户回答、受理确认和 `[可自主决定]` 代填均可追溯；
- 低风险任务未被过度流程化。
