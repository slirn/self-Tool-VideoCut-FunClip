# 存量工程规范融合规范

## 目的

本规范用于把已有工程中已经形成的规则、习惯和兼容约束接入公共规范。目标不是把两套规范合并成一份大文档，而是保留公共规范的单一来源，同时明确项目适配、历史差距和临时例外。

核心原则：

- 规范来源可以存在多个，Agent 的执行入口只能有一个。
- 公共规范负责通用底线和协作流程，项目规范负责技术事实、内部约定和适配方案。
- 项目规则可以补充、加严或等价替换公共规范，不得静默削弱公共规范中的强制规则。
- 存量工程采用渐进迁移，不允许用“历史工程”作为永久豁免理由。

## 规范来源与执行入口

最终项目结构应为：

```text
project/
├── AGENTS.md
└── .agent/
    ├── standards/
    ├── project-context.md
    ├── standards-profile.md
    └── standards.lock.json
```

各文件职责：

| 路径 | 职责 | 归属 |
| --- | --- | --- |
| `AGENTS.md` | 唯一 Agent 执行入口，只负责声明读取顺序和必要的项目入口规则 | 项目维护，受管区块由同步脚本更新 |
| `.agent/standards/` | 公共规范基线 | 公共规范仓库维护，同步覆盖 |
| `.agent/project-context.md` | 项目目标、技术栈、架构、命令和项目事实 | 项目维护 |
| `.agent/standards-profile.md` | 公共规范映射、项目补充、适配、偏离和历史差距 | 项目维护 |
| `.agent/standards.lock.json` | 已安装公共规范版本和文件清单 | 同步脚本维护 |

`AGENTS.md` 是唯一的 Agent 执行入口。其他工具入口，例如 `CLAUDE.md`、`.cursor/rules` 或其他平台配置文件，可以作为适配层存在，但不得独立定义第二套权威规则。适配层只负责指向 `AGENTS.md` 或转换工具格式。

公共规范仓库中的 README、使用说明和同步脚本不是业务项目的 Agent 执行入口。业务项目从项目根目录启动 Agent 时，以 `AGENTS.md` 为起点。

## 生效规范与优先级

项目实际生效规范按以下模型形成：

```text
公共规范基线
+ 项目技术和业务规则
+ 项目适配规则
- 经批准的临时例外
= 实际生效规范
```

发生冲突或例外时，按以下优先级处理：

1. 法律法规、合同、安全与合规要求；
2. 组织级强制规范；
3. 公共规范中的强制规则和安全红线；
4. 项目特有规范，包括补充、加严和等价替换；
5. 经批准的临时例外；
6. 单个任务中的实现决策。

项目规范不得静默削弱优先级更高且仍然适用的要求。实质性冲突必须由项目负责人明确批准，不能由 Agent 自行选择忽略其中一条。

## 冲突分类

项目规则与公共规范的关系必须使用以下稳定分类之一：

| 分类 | 含义 | 处理要求 |
| --- | --- | --- |
| `adopt` | 直接采用公共规范 | 记录已有项目规则如何迁移或删除 |
| `extend` | 项目要求更严格 | 保留项目规则，不得降低公共底线 |
| `specialize` | 目标相同，技术做法不同 | 说明等价关系、映射方式和验证证据 |
| `deviate` | 项目明确不遵守 | 由负责人批准，记录原因、影响、补偿措施和截止时间 |
| `not-applicable` | 当前项目不存在对应场景 | 记录判定依据；场景出现时重新评估 |
| `legacy-gap` | 历史工程尚未达到要求 | 记录负责人、受影响范围、迁移计划和截止时间 |

`specialize` 不等同于 `deviate`。只有项目机制仍能产生公共规范要求的可验证结果时，才能归类为 `specialize`。

## 存量工程接入流程

### 阶段一：盘点

1. 找到项目已有的 Agent 入口、工程规范、贡献指南、架构文档、CI 规则和代码约定。
2. 按安全、接口、配置、可靠性、数据库、测试、发布、可观测性和依赖等领域映射到公共规范。
3. 区分项目事实、项目补充、等价实现、真实冲突和历史差距。

### 阶段二：建立适配表

在 `.agent/standards-profile.md` 中逐项记录公共要求、项目现状、关系分类、处理方案、负责人和截止时间。无法确认的业务或技术取舍必须保留为待确认事项，不能由 Agent 静默补全。

### 阶段三：收敛入口

1. 项目已有 `AGENTS.md` 时，保留它作为唯一入口，并加入受管区块。
2. 受管区块内声明公共规范、项目上下文和项目适配表的读取顺序。
3. 受管区块外的项目内容保持不动；原有规则正文应迁移到项目上下文、项目适配表或被引用文档中。
4. 其他 Agent 工具入口应改为指向 `AGENTS.md` 的适配层，不保留平行规则正文。

受管区块固定使用以下标记：

```markdown
<!-- agent-standards:begin -->
<!-- agent-standards:end -->
```

每个 `AGENTS.md` 最多保留一个受管区块。同步脚本可以更新区块内内容，但不得覆盖区块外项目内容。

### 阶段四：渐进迁移

1. 先选择一个模块或一条业务链路试点，不进行一次性全量整改。
2. 新增代码和本次修改代码必须符合已确认规范。
3. 未修改的历史代码可以记录为 `legacy-gap`，但必须属于明确的模块边界并设置迁移期限。
4. 安全、权限、敏感数据、数据删除和不可回滚操作不得仅以历史兼容为由无限期豁免。
5. 每个迁移切片完成后运行对应验证，并更新适配表中的状态、证据和剩余差距。

## 公共规范升级

公共规范升级后：

1. 对比新增、修改和删除的规则；
2. 只重新评估受影响的映射、适配和例外；
3. 更新 `.agent/standards-profile.md`；
4. 通过同步脚本更新 `AGENTS.md` 受管区块；
5. 在业务项目中提交规范副本、锁定文件、受管区块和适配表变更。

公共规范锁文件必须同时记录发布版本和完整来源提交。同步脚本必须校验工作区干净、发布 tag 存在且指向当前 HEAD，不能仅根据人工传入的版本名称声明来源。

项目不得直接修改 `.agent/standards/` 中的公共规范副本。发现公共规范不适用时，应先确认问题是否会在多个项目重复出现；通用问题回到公共规范仓库处理，项目特有问题写入项目上下文或项目适配表。

## 验收要求

接入或升级后至少验证：

- Agent 从唯一的 `AGENTS.md` 入口开始读取规范；
- 公共基线、项目上下文和项目适配表均能被入口声明找到；
- 其他工具入口只做适配，没有定义冲突的权威规则；
- 每条冲突、偏离和不适项均有明确分类、责任人和处理结论；
- 历史差距有迁移范围和截止时间；
- 新增或修改代码符合当前已批准规范；
- 未运行的验证不得标记为通过；
- 同步后受管区块外的 `AGENTS.md` 内容保持不变。
