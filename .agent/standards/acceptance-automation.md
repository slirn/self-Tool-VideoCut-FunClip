# 验收自动化规范

## 目的

本规范用于把开发态功能验收、开发态安全验收、独立代码审查、48 小时运行、测试环境 72 小时验收及后续影子/灰度验收转化为可重复执行、可追溯和可判定的工程流程。

自动化的目标是统一执行能力，不是让每个功能重复编写调度、证据和状态管理代码。公共执行引擎负责流程、适配和判定；项目提供环境配置；具体功能提供声明式验收场景和必要的专用探针。

## 基本原则

- 验收对象必须是不可变的 commit SHA 或镜像 digest，不能用浮动分支或工作区作为验收结果的对象。
- 统一执行能力、证据格式和阶段状态机由独立共享工具提供，不得在项目内复制整套执行器。
- 项目差异通过配置、场景和适配器表达，不通过修改公共判定逻辑表达。
- 能确定性执行的检查必须自动执行并自动判定。
- 独立代码审查、威胁建模、风险接受和例外必须保留人工确认。
- 未运行的检查不得标记为通过；跳过、阻塞、失败和通过必须分开记录。
- 任何代码、配置、镜像或验收计划发生变化后，之前与之绑定的验收结果失效。

## 职责边界

| 层级 | 负责内容 |
| --- | --- |
| 公共规范仓库 | 阶段、状态机、计划/结果 Schema、证据要求、判定原则和模板 |
| 共享验收平台 | 编排、调度、适配器、执行器、长时运行、证据收集和报告 |
| 项目仓库 | 环境、启动/停止/回滚命令、阈值、业务场景和专用探针 |
| 运行基础设施 | CI、专用 Runner、密钥、对象存储、指标和日志系统 |

共享验收平台的实现、版本和发布来源不得直接复制到项目的 `.agent/standards/` 目录。项目只安装或调用经过版本锁定的 CLI、容器镜像或 CI Action。

## 验收状态机

推荐阶段顺序：

```text
DEVELOPMENT_DONE
-> AUTOMATED_REVIEW
-> INDEPENDENT_REVIEW
-> HUMAN_RISK_REVIEW
-> DEV_FUNCTIONAL_ACCEPTANCE
-> DEV_SECURITY_ACCEPTANCE
-> DEV_48H_SOAK
-> DEVELOPMENT_ACCEPTED
-> TEST_72H_ACCEPTANCE
-> SHADOW
-> CANARY
-> PRODUCTION_ACCEPTED
```

项目可以裁剪不适用的阶段，但必须记录裁剪原因和批准人。不得因为阶段尚未自动化而把检查默认为通过。

## 验收计划

验收计划必须声明：

- 项目名称和验收对象；
- commit、tag 或镜像 digest；
- 环境名称、地址和配置来源；
- 阶段、步骤、依赖和失败策略；
- 检查命令或探针；
- 通过阈值和超时；
- 需要人工签署的证明；
- 证据输出位置；
- 清理、恢复和回滚动作。

验收计划优先使用 YAML 或 JSON 声明。命令型项目可以使用已有测试框架、脚本或 CLI，但必须由统一执行器编排。

## 步骤类型

### 命令步骤

用于调用构建、测试、扫描、迁移、重启、回滚和项目脚本。必须记录：

- 完整命令；
- 工作目录；
- 环境变量来源；
- 超时；
- 预期退出码；
- stdout、stderr 和产物位置。

### HTTP 步骤

用于健康检查、接口契约和探针。必须声明 URL、方法、认证方式、超时和预期状态；断言失败必须产生可复核证据。

### 人工证明步骤

用于独立代码审查、威胁建模、风险接受和例外批准。证明必须记录：

- 审查者或批准人；
- 验收对象 commit 或 digest；
- 审查时间；
- 结论和残余风险；
- 阻塞问题及关闭状态。

自动 Agent 审查可以作为候选问题发现机制，但不能替代高风险场景下的人工作出风险判断。

### 长时运行步骤

用于开发态 48 小时和测试态 72 小时运行。必须使用真实墙钟时间，不得用短时压测代替。执行期间至少采集：

- 健康检查和关键业务探针；
- 错误率、时延、吞吐和资源趋势；
- 重启、故障注入、降级和恢复结果；
- 数据丢失、重复写入、积压和清理结果；
- 日志、指标和证据文件。

长时运行必须支持检查点、恢复、取消、超时和收尾。检查点不能替代真实运行时间。

## 功能验收

功能验收至少覆盖适用的：

- 正常路径和主要用户结果；
- 失败、边界、重复、并发和超时路径；
- 数据一致性、幂等和恢复；
- 权限、组织和租户边界；
- 升级、重启和回滚行为；
- 项目已确认的非功能要求。

功能场景优先复用项目已有的单元、集成和端到端测试，不另建一套只用于验收的重复实现。

## 安全验收

自动安全验收至少按适用性执行：

- 依赖、许可证和容器漏洞扫描；
- SAST、DAST、IaC 和密钥扫描；
- 认证、授权、越权和租户隔离矩阵；
- 输入边界、请求大小、速率和并发限制；
- 敏感数据脱敏、导出、日志和错误响应检查；
- 审计、权限变更和失败降级检查。

自动扫描通过不能单独证明安全。威胁建模、业务权限组合和高风险残余风险仍需人工批准。

## 独立代码审查

独立审查必须与实现执行者分离，至少满足：

- 使用独立会话、独立 Agent 或独立审查者；
- 以固定 commit 或 diff 为输入；
- 读取相同的规范和项目上下文；
- 输出结构化问题清单；
- blocker 和 major 必须关闭或记录经批准的例外。

自动静态检查不能替代对需求、架构边界、数据语义和兼容性的审查。

## 自动判定

只有在通过条件可计算时，程序才能自动把阶段判定为 `PASSED`。自动判定至少要求：

- 所有必需步骤成功；
- 所有阈值满足；
- 没有未批准的 blocker 或 major；
- 所有必需人工证明存在且绑定同一验收对象；
- 环境、工具和引擎版本可追溯；
- 证据完整且可读取。

任一条件不满足时，结果必须是 `FAILED`、`BLOCKED` 或 `NOT_RUN`，不能使用模糊状态。

## 证据与报告

每次运行生成一个验收报告，至少包含：

```text
project
subject.commit / subject.imageDigest
engineVersion / engineCommit
environment
stage
startedAt / finishedAt
status
steps
thresholds
evidence
attestations
exceptions
```

证据应保存到受控位置，并与验收对象和运行 ID 关联。报告和证据不得包含密钥、令牌或未经脱敏的个人敏感信息。

每次运行还应生成 `evidence-manifest.json`，对证据文件记录相对路径、大小和 SHA-256。验证工具发现文件缺失、大小变化或哈希不一致时必须判定失败。独立审查证明记录 reviewer、approved、commit 和文件哈希，并与验收对象绑定。

长时运行必须持久化运行状态，至少记录 runId、stepId、commit、计划结束时间、成功/失败计数、租约所有者、租约到期时间和状态。执行器重启后应使用同一 runId 恢复，而不是重新计算 48/72 小时。

## 版本锁定

项目应维护：

```text
.agent/acceptance.lock.json
```

至少记录：

- 共享验收平台版本和来源提交；
- 使用的适配器版本；
- 验收计划和策略版本；
- 最后通过的环境、验收对象和报告 ID。

公共规范升级、平台升级或验收计划变化后，必须重新运行受影响阶段。

## 第三方工程接入

第三方工程应按 `docs/ACCEPTANCE-PLATFORM-INTEGRATION.md` 的固定步骤接入。共享执行平台提供 `acceptance init` 命令，用于创建项目验收配置、验收计划、验收锁文件、功能/安全/长时运行目录和 attestation 目录。

初始化时优先读取目标工程已有的 `.agent/standards.lock.json`，把规范版本和来源提交写入 `.agent/acceptance.lock.json`。正式验收必须使用不可变 commit 或镜像 digest。

快速接入流程：

```text
1. 同步 Agent-Engineering-Standards v0.14.0
2. 登录 GHCR 并确认可拉取 Agent-Acceptance-Platform v0.2.0
3. 在目标工程根目录执行 acceptance init .
4. 修改 .agent/acceptance-profile.yaml 中的项目命令和环境
5. 修改 acceptance.yaml 中的检查、探针、阈值和验收对象
6. 执行 acceptance validate 和 acceptance run --dry-run
7. 生成独立审查 attestation
8. 依次执行 review、functional、security 和必要的 stability 阶段
```

`acceptance init` 支持 `generic`、`spring-boot-maven`、`node-typescript`、`python-fastapi`、`dotnet`、`vue` 和 `react` 模板。模板生成默认命令，项目仍必须确认命令和业务语义。

使用固定镜像：

```powershell
docker run --rm `
  -v "${PWD}:/workspace" `
  -w /workspace `
  ghcr.io/slirn/agent-acceptance-platform:v0.2.0 `
  init .
```

`.agent/acceptance.lock.json` 必须记录规范版本和来源提交、验收平台版本和来源提交、验收计划路径及当前验收对象。任何代码、配置、镜像或计划变化后，相关阶段的旧结果失效。

## 例外与失败

例外必须记录原因、风险、补偿措施、批准人和到期时间。安全、权限、数据删除和不可回滚操作不得仅通过延长例外绕过。

自动任务失败后：

1. 保存现场和证据；
2. 区分产品缺陷、环境问题、测试缺陷和工具问题；
3. 对可重放的瞬时故障进行有界重试；
4. 对确定性失败先修复根因；
5. 任何代码或配置修复后重新建立固定验收对象。

## 验收

- 验收对象不可变且可追溯；
- 统一执行器完成阶段编排、证据和报告；
- 项目只提供配置、场景和必要探针；
- 功能和安全检查能够阻止确定性失败；
- 独立审查和人工风险判断有明确证明；
- 48/72 小时运行使用真实墙钟时间并支持恢复；
- 验收结果不能跨 commit、镜像或配置变化复用。
- 新建接入工程可以通过 `acceptance init` 建立一致的目录、锁文件和计划骨架。
