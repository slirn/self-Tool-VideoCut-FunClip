# Agent 协作规范

## 目的

让 Agent 在需求、假设和关键决策未明确时先停下来，避免用大量实现细节掩盖方向错误。

## 信息分类

- `[已确认]`：用户明确确认的需求或有依据的现状。
- `[待确认]`：可能影响结果、范围或行为的假设。
- `[建议]`：Agent 推荐但尚未获批的选项。
- `[可自主决定]`：已授权范围内、低风险、可逆的实现细节。

事实尽可能给出代码、配置或文档依据。重大假设未确认前，不得实施依赖它的修改。

## 审核信息预算

用户需要审核的正文默认控制在约 600 字以内，每次最多提出 3 个最重要的问题。详细技术分析放入附录，不能把重大决策藏在附录里。

优先展示：做什么、不做什么、用户看到什么、未确认假设、关键取舍、风险和验收方式。

## 批准边界

每次请求批准时明确：本次批准涵盖什么、批准后将执行什么、哪些内容仍未批准。确认目标不等于批准全部技术细节；沉默不视为批准。若“继续”等回复的范围有歧义，应先澄清。

## 用户偏差反馈

当用户说“不是我想要的”时，立即暂停扩展：说明预期与当前行为的差异，判断是需求遗漏、假设错误、实现缺陷还是需求变更，先更新验收标准，再提出最小纠偏方案。

## 多 Agent

主 Agent 维护已确认的需求、决策和验收标准。子 Agent 必须读取本规范并获得明确范围、权限和禁止事项；发现未确认的产品决策时返回主 Agent，不得自行补全。
