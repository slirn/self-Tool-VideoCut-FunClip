# 技术债治理规范

## 目的

本规范用于防止临时妥协、历史缺口和未知风险变成永久设计。技术债不是禁止负债，而是要求负债可见、有负责人、有风险边界和退出条件。

## 什么属于技术债

- 已知但尚未修复的缺陷或脆弱实现；
- 为赶进度采用的临时方案；
- 因兼容或迁移保留的重复实现；
- 缺失的测试、监控、文档或自动化；
- 已过期但仍在使用的依赖、接口或配置；
- 因历史原因无法满足当前质量门禁的区域。

正常且可接受的实现选择不是技术债。不能因为代码“不够漂亮”就建立债务项。

## 记录要求

每项技术债至少记录：

| 字段 | 内容 |
| --- | --- |
| ID | 稳定唯一标识 |
| 问题 | 具体缺陷或风险，不写笼统的“需要重构” |
| 来源 | 为什么产生，关联事故、任务或决策 |
| 影响 | 对业务、数据、安全、性能或维护的影响 |
| 当前缓解 | 已有的监控、限制或补偿措施 |
| 负责人 | 必须有人负责，不能匿名 |
| 触发条件 | 什么情况下必须优先处理 |
| 截止时间 | 最晚复核或关闭时间 |
| 整改方案 | 最小可验证的退出路径 |
| 状态 | `open`、`mitigated`、`scheduled`、`closed` 或 `accepted` |

`accepted` 必须说明风险为什么可接受以及何时复核，不能作为永久忽略。

## 债务产生

以下情况必须登记技术债：

- 无法立即修复但已有已知风险的临时方案；
- 质量门禁或公共规范例外；
- 无法从根源修复而采用的补丁；
- 存量工程接入时标记的 `legacy-gap`；
- 事故复盘中未立即完成的非紧急纠正项。

不得用 TODO 注释代替可追踪债务。代码内可保留 TODO，但必须关联债务 ID 或任务记录。

## 处理原则

- 新增代码和本次修改区域优先消除新债务；
- 高风险安全、权限、数据和不可回滚问题不得只登记不处理；
- 同一债务重复影响交付时，应提升优先级而不是继续延期；
- 整改按可验证切片推进，不要求一次性重构；
- 关闭债务必须有验证证据，不能只凭代码已修改。

## 复核节奏

项目必须定义债务复核节奏。至少以下时点需要检查：

- 发布前，确认未引入新的高风险债务；
- 债务到期前；
- 相关模块发生重大修改、迁移或事故时；
- 定期治理评审时。

长期未关闭的债务应由负责人重新确认风险、期限和处理路线。

## 验收

- 技术债有明确问题和影响；
- 每项债务有负责人和截止时间；
- 高风险债务有缓解和升级路径；
- 到期债务被处理、重排或明确接受；
